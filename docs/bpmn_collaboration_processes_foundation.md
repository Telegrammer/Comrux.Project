# BPMN 2.0 L1: каноническая модель верхнего уровня

Документ фиксирует единую L1-модель (первый уровень BPMN 2.0) для платформы
коллаборативной разработки. Цель: сохранить роли из use-case диаграммы и
показать параллельность ключевых процессов без перегрузки деталями реализации.

## 1. Граница модели L1

### 1.1 In scope (что рисуем на L1)

- роли пользователей и их участие в процессах;
- межсервисные пулы `Auth`, `Project`, `Collab`, `Chat`, `Фоновый обработчик`;
- верхнеуровневые подпроцессы (collapsed subprocess);
- точки проверки доступа;
- точки параллельного запуска рабочих контуров;
- асинхронный релизный контур через message flow.

### 1.2 Out of scope (что не рисуем на L1)

- конкретные HTTP endpoints, middleware, токены и криптографию;
- детальные CRUD-операции;
- детали хранения (Redis/DB/Object Storage), retry/backoff, технические воркеры;
- внутренние алгоритмы авторизации и маршрутизации сообщений.

## 2. Участники (Pools/Lanes)

### 2.1 Пользовательский пул

Пул: `Пользовательский контур`.

Дорожки (lanes):

- `Участник`;
- `Куратор`;
- `Владелец`.

Примечание: роль "Пользователь" трактуется как внешний актор до входа в проектный
контекст и на L1 отдельной дорожкой не выделяется.

### 2.2 Сервисные пулы

- `Comrux.Auth`;
- `Comrux.Project`;
- `Comrux.Collab`;
- `Comrux.Chat`;
- `Фоновый обработчик`.

## 3. Канонические подпроцессы L1

На L1 используются только эти подпроцессы:

1. `Authentication and Session Context` (`Comrux.Auth`);
2. `Project Governance` (`Comrux.Project`);
3. `Collaborative Editing` (`Comrux.Collab`);
4. `Project Chat Communication` (`Comrux.Chat`);
5. `Task Management` (`Comrux.Project`);
6. `Release Build Pipeline` (`Comrux.Project` + `Фоновый обработчик`).

Эти 6 блоков являются единственным "source of truth" для отрисовки L1.

## 4. Основная последовательность L1

1. `Пользовательский контур -> Comrux.Auth`:
   `Вход в платформу`.
2. `Comrux.Auth -> Comrux.Project`:
   `Передача контекста сессии`.
3. `Comrux.Project`:
   `Project Governance`.
4. В `Project Governance`:
   `Exclusive Gateway: Разрешено работать в проектном контуре?`.
5. При `Нет`:
   завершение ветки `Доступ запрещен`.
6. При `Да`:
   `Parallel Gateway (split)` на три параллельные ветви:
   - `Collaborative Editing`;
   - `Project Chat Communication`;
   - `Task Management`.
7. `Release Build Pipeline` инициируется из `Comrux.Project` как самостоятельный
   верхнеуровневый процесс (не обязательный финальный шаг каждой пользовательской сессии).
8. `Comrux.Project <-> Фоновый обработчик`:
   асинхронная обработка релиза и возврат статуса (`READY`/`FAILED`).

## 5. Параллельность L1

Единственная обязательная точка параллельности на L1:

- после проверки доступа в `Comrux.Project` одновременно запускаются:
  - контур совместного редактирования (`Collab`);
  - контур коммуникации (`Chat`);
  - контур управления задачами (`Task Management`).

Это отражает реальную одновременность рабочей активности и заменяет линейную
цепочку операций.

## 6. Ролевая интерпретация на L1

### 6.1 Участник

- участвует в `Collaborative Editing`;
- участвует в `Project Chat Communication`;
- исполняет назначенные задачи в `Task Management`.

### 6.2 Куратор

- участвует в `Project Governance` (участники, роли, группы, доступ);
- участвует в `Task Management` (постановка и назначение задач);
- при необходимости участвует в запуске релизного контура.

### 6.3 Владелец

- полный контур `Project Governance` (включая стратегические изменения проекта);
- контроль `Release Build Pipeline`.

## 7. Трассировка use-case диаграммы в L1-подпроцессы

| Группа use-case | L1 subprocess |
|---|---|
| Вход, доступ к платформе, сессия | `Authentication and Session Context` |
| Создание/ведение проекта, роли, участники, приватность, ACL | `Project Governance` |
| Совместное редактирование контента | `Collaborative Editing` |
| Коммуникация через чат | `Project Chat Communication` |
| Назначение и выполнение задач | `Task Management` |
| Выгрузка/фиксация состояния проекта | `Release Build Pipeline` |

## 8. Message flow каталог для L1

Использовать только следующие межпуловые связи:

1. `Пользовательский контур -> Comrux.Auth`:
   `Запрос входа`.
2. `Comrux.Auth -> Comrux.Project`:
   `Контекст сессии`.
3. `Comrux.Project -> Comrux.Collab`:
   `Контекст совместной работы`.
4. `Comrux.Project -> Comrux.Chat`:
   `Контекст коммуникации`.
5. `Comrux.Project -> Фоновый обработчик`:
   `Запуск формирования релиза`.
6. `Фоновый обработчик -> Comrux.Project`:
   `Статус релиза`.

Другие message flow на L1 не добавляются.

## 9. Нормативные правила отрисовки (анти-паутина)

- не рисовать на L1 отдельные задачи для каждого CRUD-действия;
- не соединять `Collab`, `Chat`, `Task Management` в линейную последовательность;
- не дублировать проверку доступа в нескольких местах L1;
- не показывать внутренности `Auth` (валидация токена, refresh и т.п.);
- не использовать более одного параллельного split для рабочего контура;
- все дополнительные детали переносить на L2.

## 10. Критерии готовности L1

Диаграмма считается корректной, если:

1. присутствуют все 5 сервисных пулов и пользовательский пул с 3 дорожками;
2. присутствуют ровно 6 канонических подпроцессов;
3. есть один `Exclusive Gateway` проверки доступа;
4. есть один `Parallel Gateway` запуска рабочих ветвей;
5. релизный контур показан как асинхронный и независимый от линейного пользовательского пути;
6. отсутствуют технические детали реализации.

## 11. Следующий шаг (за пределами текущего документа)

После фиксации L1 допускается построение L2:

- отдельно для `Project Governance`;
- отдельно для `Collaborative Editing`;
- отдельно для `Release Build Pipeline`.

L2 не должен менять структуру L1, а только декомпозировать ее.
